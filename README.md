# Stellar Classification
 
Predicting whether an astronomical observation is a `GALAXY`, `QSO` (quasar), or `STAR` from photometric and spectral survey data — built as a production-style ML pipeline rather than a single monolithic notebook.
 
**Final result:** single tuned XGBoost model, Stratified 5-Fold CV macro F1 = **0.9563**.
 
## Repository Structure
 
```
stellar-classification/
├── notebooks/
│   ├── 01_eda.ipynb                 # Target distribution, feature distributions, data quality checks
│   ├── 02_preprocessing.ipynb       # Target + categorical encoding, cleaning
│   ├── 03_baseline_models.ipynb     # 4-model comparison (LogReg, LightGBM, XGBoost, CatBoost)
│   ├── 04_feature_engineering.ipynb # Color-index features, log-redshift, SHAP importance
│   ├── 05_optuna_tuning.ipynb       # 40-trial Bayesian hyperparameter search
│   ├── 06_ensemble.ipynb            # Blending/stacking vs. single-model comparison
│   └── 07_final_submission.ipynb    # Test-set inference + Kaggle submission file
├── results/                         # CV metrics per stage (csv), for auditing without re-running notebooks
├── submissions/                     # Generated Kaggle submission file
├── .gitignore
├── requirements.txt
└── README.md
```
 
`data/` and `models/` are intentionally not tracked in git (see [Setup](#setup) below) — the raw CSVs are large, and trained model artifacts are binary and easily regenerated by re-running the notebooks in order.
 
## Setup
 
```bash
conda create -n stellar python=3.11 -y
conda activate stellar
pip install -r requirements.txt
```
 
Then place the competition files here before running anything:
 
```
data/
├── train.csv
├── test.csv
└── sample_submission.csv
```
 
Run the notebooks **in order, 01 → 07** — each one reads artifacts written by the previous one (processed datasets, fitted encoders, trained models). `data/processed/`, `models/`, and `results/` are created automatically as you go.
 
## Pipeline & Results
 
| Stage | Notebook | Result |
|---|---|---|
| EDA | `01_eda.ipynb` | Moderate class imbalance (65% GALAXY / 20% QSO / 14% STAR); `redshift` is the single most discriminative feature; no missing data or duplicates |
| Preprocessing | `02_preprocessing.ipynb` | Target label encoding + one-hot categorical encoding; numeric scaling deliberately deferred to per-fold pipelines to avoid CV leakage |
| Baselines | `03_baseline_models.ipynb` | XGBoost best of 4 models, **CV macro F1 = 0.9564**; dominant error mode identified as `STAR`→`GALAXY` confusion |
| Feature Engineering | `04_feature_engineering.ipynb` | Added SDSS-style color indices (`u-g`, `g-r`, `r-i`, `i-z`, `u-r`, `g-i`) + log-redshift. `color_g_i` became XGBoost's #1 feature by gain, but CV barely moved (0.9556) — the model already approximated this signal from raw bands |
| Hyperparameter Tuning | `05_optuna_tuning.ipynb` | 40-trial Optuna (TPE) search recovered the lift to **CV macro F1 = 0.9563**, at ~2x training cost |
| Ensembling | `06_ensemble.ipynb` | Simple average, weighted average, and stacking all tested — **none beat the single tuned model**. Shipped the single model instead of unnecessary complexity |
| **Final Submission** | `07_final_submission.ipynb` | Single tuned XGBoost, full pipeline validated end-to-end against training-time schema before writing `submissions/submission.csv` |
 
Every CV score above comes from **Stratified 5-Fold cross-validation** (not a single train/test split), with per-fold accuracy, macro F1, training time, and inference time tracked throughout.
 
## Key Engineering Decisions
 
- **Notebook-per-stage, not one monolithic notebook.** Each notebook has one clearly-scoped job and states its inputs/outputs at the top.
- **Every model-building notebook defines fresh, unfit estimators per CV fold** (factory functions, not shared instances) — a common source of silent CV leakage.
- **Numeric scaling is fit inside CV folds only**, never globally before splitting, to avoid leaking validation-fold statistics into training.
- **Out-of-fold (OOF) predictions**, not in-sample predictions, drive every confusion matrix and ensembling decision in this project.
- **Claims are checked against actual numbers before being written down.** Several early hypotheses in this project (e.g. which categorical feature might leak the target, which classes would be most confused) turned out to be wrong when checked against real data, and were corrected rather than left in — see the notebooks' markdown cells for specifics.
## Known Limitation
 
`STAR` is consistently the hardest class to classify (F1 ≈ 0.93 vs. 0.96–0.98 for the other two), with its dominant error being misclassification *as* `GALAXY` (~6.9% of true `STAR` rows) — a pattern that persisted, essentially unchanged, through feature engineering, hyperparameter tuning, and every ensembling strategy tried. This points to genuine ambiguity in a subset of faint, low-redshift objects rather than a fixable modeling choice, and is a natural candidate for future work if additional data (e.g. imaging morphology) becomes available.
